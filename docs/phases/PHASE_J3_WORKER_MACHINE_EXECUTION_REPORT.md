## 1. Phase Objective

Phase J.3 connects actual workshop operations (`OperationExecution`) with physical resources:
1. **The Artisan / Worker** executing the operation (`worker_id`).
2. **The Machine / Equipment** utilized during processing (`machine_id`).

In Phase J.1 and J.2, operations transitioned between routing states (`PENDING` $\rightarrow$ `READY` $\rightarrow$ `IN_PROGRESS` $\rightarrow$ `COMPLETED`). However, operations could proceed without verifying workshop personnel or equipment assignments. Phase J.3 transforms this baseline:
- An operation becomes **READY** and awaits allocation of an **eligible artisan** and **compatible machine**.
- Explicit resource assignment endpoints allow claiming or assigning resources.
- Operation start transitions (`READY` $\rightarrow$ `IN_PROGRESS`) strictly enforce resource requirements, skill matching, machine compatibility, and non-concurrent availability.
- A critical distinction is maintained between **Planned Resources** (`ScheduledTask.worker_id`, `ScheduledTask.machine_id` generated by CP-SAT) and **Actual Resources** (`OperationExecution.worker_id`, `OperationExecution.machine_id`).
- When operations complete, resources are immediately released for subsequent operations, without automatic or inappropriate resource inheritance across sequential steps.

## 2. J.1 / J.2 Architecture Audited

### J.1 Foundation (Data Model & Idempotency)
- `OperationExecution` represents workshop floor reality; `ScheduledTask` represents planning.
- Each `ProductionOrder` has sequential operations mapped to `ProductionStep` records.
- Initialized orders set Step 1 to `READY` and subsequent steps to `PENDING`.
- Existing foreign keys on `OperationExecution`:
  - `worker_id: Mapped[Optional[uuid.UUID]] = mapped_column(ForeignKey("workers.id", ondelete="SET NULL"), nullable=True)`
  - `machine_id: Mapped[Optional[uuid.UUID]] = mapped_column(ForeignKey("machines.id", ondelete="SET NULL"), nullable=True)`
- Existing relationships: `worker = relationship("Worker")`, `machine = relationship("Machine")`.

### J.2 Foundation (Workflow & Sequential Routing)
- Sequential transitions: `PENDING` $\rightarrow$ `READY` $\rightarrow$ `IN_PROGRESS` $\rightarrow$ `COMPLETED`, with support for `PAUSED` and `BLOCKED`.
- Predecessor enforcement: Step $N$ cannot start or advance to `READY` until Step $N-1$ is `COMPLETED`.
- Atomic progression: Upon completing Step $N$, Step $N+1$ transitions from `PENDING` to `READY` within the same database transaction.
- Row-level locking (`with_for_update`) during state transitions to prevent race conditions.
- Progress reconciliation: Updates order status (`in_production`, `completed`) and metrics.

### Key Audit Finding
`OperationExecution` already contained `worker_id` and `machine_id` columns with relationships to `Worker` and `Machine`. No new database tables or schema alterations were required. The schema is 100% sufficient for Phase J.3.

## 5. Skill Compatibility Logic

### Deterministic Matching Algorithm
The system matches an artisan's skills against `ProductionStep.required_skill` deterministically:
1. Normalizes skills to lowercase and strips extraneous whitespace.
2. Supports comma-delimited multi-skill workers (e.g., `"stone_setting, micro_pave, assembly"`).
3. Evaluates direct equality and substring token matching:
   - If required skill is `"stone_setting"`, worker skills `["stone_setting", "polishing"]` match.
   - Rejects workers possessing incompatible skills (e.g., a caster assigned to a stone setting step).
4. If `ProductionStep.required_skill` is None, empty, or `"none"`, any worker (or no worker) is permitted.
5. Rejection produces an HTTP 409 `AppException` with code `WORKER_INELIGIBLE_SKILL`.

---

## 6. Machine Compatibility Logic

### Deterministic Type Matching
The system matches equipment against `ProductionStep.required_machine_type`:
1. Normalizes machine type to lowercase and strips extraneous whitespace.
2. Performs deterministic functional equivalence:
   - Required `"casting_furnace"` matches machine `"casting_furnace"` or generic equivalent `"furnace"`.
   - Incompatible equipment (e.g., assigning a `"laser_engraver"` to a casting operation) is rejected.
3. If `ProductionStep.required_machine_type` is None, empty, or `"none"` (e.g., manual bench tasks), no machine is required.
4. Rejection produces an HTTP 409 `AppException` with code `MACHINE_INCOMPATIBLE_TYPE`.

## 7. Assignment Workflow

Two dedicated assignment endpoints are provided:
- `POST /api/v1/production/executions/{execution_id}/assign-worker`
  - Body: `{"worker_id": "<uuid>"}`
- `POST /api/v1/production/executions/{execution_id}/assign-machine`
  - Body: `{"machine_id": "<uuid>"}`

### Assignment Steps:
1. **Authenticate User**: Extract `user_id` from JWT session.
2. **Verify Execution Ownership**: Verify `OperationExecution.user_id == user_id` with row-locking (`for_update=True`).
3. **Verify State**: Disallow assignment to `COMPLETED` executions (`EXECUTION_ALREADY_COMPLETED`, HTTP 409).
4. **Verify Resource Ownership**:
   - Query resource filtering on `id == requested_id AND user_id == user_id`.
   - If missing or belonging to another tenant, raise `WORKER_NOT_FOUND` / `MACHINE_NOT_FOUND` (HTTP 404).
5. **Verify Eligibility**:
   - For worker: check `is_worker_skill_eligible` against `step.required_skill`.
   - For machine: check `is_machine_compatible` against `step.required_machine_type`.
6. **Atomic Update**: Set `execution.worker_id` / `execution.machine_id` and commit. Assignment does NOT alter execution state (`READY` remains `READY`).

## 8. Start Validation (READY $\rightarrow$ IN_PROGRESS)

When starting an operation:
1. Inspect the linked `ProductionStep`:
   - Determine `worker_required` from `step.required_skill`.
   - Determine `machine_required` from `step.required_machine_type`.
2. Inspect tenant resources:
   - If tenant has registered workers and the step requires a worker, `execution.worker_id` must be assigned. If missing, raise `MISSING_REQUIRED_WORKER` (HTTP 409).
   - If tenant has registered machines and the step requires a machine, `execution.machine_id` must be assigned. If missing, raise `MISSING_REQUIRED_MACHINE` (HTTP 409).
3. Validate assigned worker skill and machine type compatibility.
4. Run concurrency conflict check for worker and machine.
5. If all validations succeed, set `status = IN_PROGRESS` and record `actual_start_time = now(UTC)`.

## 9. Resource Availability

Static and dynamic availability are separated:
- **Static Availability**: `Worker.is_available`, `Machine.is_available` (database flags).
- **Dynamic Workshop Availability**: An active execution check querying `OperationExecution`:
  - A resource is **UNAVAILABLE** if actively engaged in another execution with status `IN_PROGRESS` or `PAUSED`.
  - A resource is **AVAILABLE** if not assigned to any non-terminal execution, or if all its executions are `COMPLETED`, `BLOCKED`, `READY`, or `PENDING`.

Reusable helpers:
- `production_execution_service.is_worker_available(db, user_id, worker_id, exclude_execution_id)`
- `production_execution_service.is_machine_available(db, user_id, machine_id, exclude_execution_id)`

## 10. Resource Conflict Handling

When an execution attempts to transition to `IN_PROGRESS`:
1. Row-lock candidate active executions:
   ```sql
   SELECT id, status FROM operation_executions
   WHERE user_id = :user_id
     AND worker_id = :worker_id
     AND status IN ('in_progress', 'paused')
     AND id != :exclude_execution_id
   FOR UPDATE
   ```
2. If another active execution exists:
   - For worker: raise `WORKER_RESOURCE_CONFLICT` (HTTP 409).
   - For machine: raise `MACHINE_RESOURCE_CONFLICT` (HTTP 409).
3. **Paused State Retention**: A `PAUSED` operation retains physical custody of its artisan and equipment. Another operation cannot claim them while paused.

## 11. Planned vs Actual Resource Distinction

| Property | Planned (`ScheduledTask`) | Actual (`OperationExecution`) |
|---|---|---|
| Source of Truth | CP-SAT mathematical optimization solver | Actual workshop execution records |
| Worker ID | `ScheduledTask.worker_id` | `OperationExecution.worker_id` |
| Machine ID | `ScheduledTask.machine_id` | `OperationExecution.machine_id` |
| Time Tracking | `scheduled_start_time`, `scheduled_end_time` | `actual_start_time`, `actual_end_time` |
| Duration | `planned_duration_hours` | `actual_duration_hours` |
| Mutation | Immutable once scheduled; records the plan | Updates dynamically as artisans claim tasks |

### API Response Structure
`OperationExecutionResponse` explicitly provides:
- `worker_id` / `actual_worker_id`: Actual artisan executing the step.
- `machine_id` / `actual_machine_id`: Actual machine utilized.
- `planned_worker_id` / `planned_worker_name`: Planned artisan from CP-SAT `ScheduledTask`.
- `planned_machine_id` / `planned_machine_name`: Planned machine from CP-SAT `ScheduledTask`.
- `worker_eligible`: Boolean flag indicating craft skill match.
- `machine_compatible`: Boolean flag indicating equipment type match.

## 12. Reassignment Rules

State-dependent resource reassignment matrix:

| State | Worker Reassignment | Machine Reassignment | Rationale |
|---|---|---|---|
| `READY` | **Allowed** | **Allowed** | Prior to work start, workshop dispatcher can assign or reassign resources. |
| `PENDING` | **Allowed** | **Allowed** | Staging state before predecessor completion. |
| `BLOCKED` | **Allowed** | **Allowed** | When halted due to an issue, resources may be reassigned. |
| `IN_PROGRESS` | **Rejected** (409) | **Rejected** (409) | Prevents corrupting the active audit trail during execution. |
| `PAUSED` | **Rejected** (409) | **Rejected** (409) | Active execution holds resource custody while temporarily halted. |
| `COMPLETED` | **Rejected** (409) | **Rejected** (409) | Terminal execution history is immutable. |

## 13. Transaction & Concurrency Strategy

1. **Row-Level Locking**: In PostgreSQL, queries validating status and detecting conflicts utilize `SELECT ... FOR UPDATE` via `with_for_update()`.
2. **Atomic State & Advancement**: All checks, assignments, state transitions, predecessor validations, and subsequent step advancements execute within a single atomic database transaction (`db.commit()`).
3. **SQLite Support**: The test environment employs SQLite in-memory with transactions. For row-locking compatibility, the implementation guards against driver differences while enforcing strict transaction boundaries.

## 16. Security & Multi-Tenant Isolation

1. **Tenant Filtering**: All resource queries include `user_id == current_user.id`.
2. **IDOR Prevention**: Assigning a worker or machine belonging to Tenant B on Tenant A's execution returns HTTP 404 (`WORKER_NOT_FOUND` / `MACHINE_NOT_FOUND`), revealing no existence or metadata of foreign tenant records.
3. **Payload Sanitization**: Pydantic schemas enforce `extra="forbid"`, rejecting injection of `user_id`, timestamps, or state override fields.
4. **Server-Generated Timestamps**: UTC server timestamps are authoritative for all transitions.

## 19. Known Limitations

1. **Static Shift Schedules**: Phase J.3 checks dynamic availability against active executions (`IN_PROGRESS`, `PAUSED`). It does not calculate calendar shift hours or lunch breaks.
2. **Partial Multi-Resource Stations**: Each operation links to at most one primary worker and one primary machine. Multi-artisan team operations (e.g., master + apprentice pairs) will be supported in future expansions.
3. **Database Concurrency in SQLite**: SQLite uses database-level locks rather than PostgreSQL's row-level `SELECT ... FOR UPDATE`. In production environments under PostgreSQL, full row-locking is active.
